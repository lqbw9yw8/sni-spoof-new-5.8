### ۷ 🔴 `self_update.rs` — سه ایراد هم‌زمان

**۷الف. تزریق مسیر در URL API (شدید)**
```rust
let api_url = format!("https://api.github.com/repos/{}/releases/latest", repo);
```
`repo` مستقیم از `update_repo` در فایل TOML می‌آید و `config.rs::validate()`
**هیچ بررسی‌ای رویش ندارد** (تأیید شد: تنها ارجاع‌ها خطوط ۲۴۸/۳۱۸/۴۰۰ و
همه فقط مقدار پیش‌فرض‌اند). مقداری مثل
`../../repos/attacker/evil` یا `x/y?foo=` مسیر درخواست را عوض می‌کند.

**✅ رفع انجام‌شده:** تابع `self_update::validate_repo_slug()` اضافه شد و
در **دو نقطه** اجبار می‌شود — هم در `config::validate()` (خط ۷۵۲) و هم در
ابتدای خود `check_for_update()` (چون تابع `pub` است و هر فراخوانی‌کننده‌ای
می‌تواند رشتهٔ دلخواه بدهد). قواعد: باید دقیقاً یک `/` داشته باشد، هر دو
نیمه فقط `[A-Za-z0-9._-]`، هیچ نیمه‌ای `.` یا `..` نباشد، و کل رشته ≤ ۲۰۱
کاراکتر. همین منطق در `uitest/mock-server.mjs` هم آینه شد تا تست‌های UI
آن را بپوشانند.

**تأیید:** هر ۱۹ ورودی خصمانه (شامل `a/b/../../other`، `a/b?x=y`،
`https://api.github.com/repos/a/b`، `user:pass@host/repo`، `owner//repo`،
`a/.`، `./b`) رد شدند و هر ۴ ورودی معتبر پذیرفته شدند — با شبیه‌سازی
مستقل منطق در پایتون بررسی شد.

**۷ب. مخزن پیش‌فرض اشتباه**
```rust
pub const DEFAULT_UPDATE_REPO: &str = "lqbw9yw8/sni-spoof-new-5.5";
```
این مخزن **۵.۶** است. کامنت بالای همین ثابت با آب‌وتاب توضیح می‌دهد که
قبلاً `4.4` و `2.3.4` اشتباه بودند و «رفع شد» — ولی باز هم نسخهٔ قبلی مانده.

**۷پ. ادعای SHA-256 دروغ است**
doc-comment خط ۴ می‌گوید «downloads the binary, verifies SHA-256, and
replaces the current executable». در واقعیت:
- `sha256: None,  // Would need a separate checksums file`
- **هیچ تابع دانلود یا نصبی وجود ندارد** (تأیید شد با grep).
ماژول فقط یک بررسی نسخه است. مستندات باید تصحیح شود وگرنه کاربر تصور
می‌کند به‌روزرسانی امن دارد.

**✅ رفع انجام‌شده (۷ب و ۷پ):**
- ثابت به `lqbw9yw8/sni-spoof-new-5.6` اصلاح شد، و تست
  `default_repo_matches_this_crate` آن را **پین** می‌کند تا ارتقای بعدی
  نسخه نتواند برای بار چهارم بی‌صدا این اشتباه را تکرار کند.
- `README.md` و `uitest/mock-server.mjs` هم به ۵.۶ به‌روز شدند
  (mock-server آینهٔ `Settings::default()` است و باید هم‌گام بماند).
- doc-comment بازنویسی شد: برچسب ماژول از `[DONE]` به **`[PARTIAL]`**
  تغییر کرد و بخش «Scope — read this before trusting the module name»
  صریحاً می‌گوید این ماژول فقط بررسی می‌کند، دانلود/نصب ندارد، و
  `sha256` همیشه `None` است. یک هشدار هم اضافه شد که اگر روزی نصب‌کننده
  اضافه شد، **باید** امضا یا checksum خارج از باند را راستی‌آزمایی کند
  وگرنه مسیر اجرای کد از راه دور می‌شود.
- تست `update_info_carries_no_unverified_digest` این قرارداد را قفل می‌کند.

### ۸ 🟠 `singleton.rs::drop` — حذف بی‌قید فایل قفل

```rust
// Best-effort remove; if another instance raced us leave its file.
let _ = std::fs::remove_file(&self.path);
```
کامنت درست است ولی کد خلافش را می‌کند: فایل **بدون هیچ بررسی** حذف می‌شود.
سناریو:
1. نمونهٔ A خارج می‌شود → قفل آزاد، ولی هنوز `remove_file` نکرده
2. نمونهٔ B قفل را می‌گیرد (فایل هنوز هست)
3. A حالا `remove_file` می‌کند → فایل قفلِ **B** پاک شد
4. نمونهٔ C فایل جدید می‌سازد و قفل می‌گیرد → **B و C هم‌زمان اجرا**

دو نمونهٔ هم‌زمان یعنی دو WinDivert handle و رقابت روی پورت رله — دقیقاً
همان چیزی که این ماژول برای جلوگیری‌اش نوشته شده.

**✅ رفع انجام‌شده:** `remove_file` **به‌کلی حذف شد** — فایل قفل عمداً روی
دیسک باقی می‌ماند. دلیلش در doc-comment مفصل ثبت شد: هیچ راه قابل حملی
برای گفتن «فقط اگر این هنوز همان entry‌ای است که من قفل کردم unlink کن»
وجود ندارد، و فایل قفل خالی هیچ هزینه‌ای ندارد و اجرای بعدی
(`OPEN_ALWAYS` / `create(true)`) دوباره از همان استفاده می‌کند. نگه‌داشتن
فایل باعث می‌شود `acquire()` بعدی روی **همان inode** رقابت کند — که کل
هدف ماژول است.

تست جدید `drop_releases_the_lock_but_keeps_the_file` هر دو نیمهٔ قرارداد
را بررسی می‌کند: بعد از `drop` فایل باید هنوز موجود باشد **و** قفل باید
واقعاً آزاد شده باشد (با یک `flock` غیرمسدودکنندهٔ تازه روی همان مسیر).

### ۹ 🟠 `pipeline.rs` — دو نگاشت بدون سقف

| نگاشت | سقف | محل درج |
|---|---|---|
| `flows` | ۲۵۶ ✅ | خط ۷۳۴ |
| `recent` | ۵۱۲ ✅ | خط ۷۵۱ |
| `relay_flows` | ۲۵۶ ✅ | خط ۱۵۴ |
| **`last_activity`** | **هیچ** ❌ | خط ۶۳۳ — هر بستهٔ TCP |
| **`inbound_ttl`** | **هیچ** ❌ | خط ۳۱۷ — هر بستهٔ ورودی وقتی autottl روشن است |

هر دو کلیدشان از IP/پورت مبدأ می‌آید که مهاجم کنترلش می‌کند. تنها مکانیزم
پاکسازی `flush_idle` است که بر اساس `idle_timeout_secs` کار می‌کند
(پیش‌فرض ۱۲۰ ثانیه، قابل تنظیم تا ۸۶۴۰۰). با یک اسکن پورت با IP جعلی، بین
دو پاکسازی حافظه نامحدود رشد می‌کند. سه نگاشت دیگر دقیقاً برای همین سقف
دارند — این دو از قلم افتاده‌اند.

**✅ رفع انجام‌شده:** `MAX_LAST_ACTIVITY = 4096` و `MAX_INBOUND_TTL = 4096`
اضافه شدند، هرکدام با تابع تخلیهٔ اختصاصی که **نصف قدیمی‌ترین** ورودی‌ها را
حذف می‌کند.

دو نکتهٔ طراحی:
- تخلیه **قدیمی‌ترین‌محور** است، نه دلخواه (برخلاف `recent` که مقدارش
  timestamp نیست). چون مقدار هر دو نگاشت خودش زمان است، ورودی‌هایی حذف
  می‌شوند که به‌هرحال نزدیک انقضا بودند — پس یک flow زنده که هنوز ترافیک
  می‌فرستد timestamp تازه دارد و **قربانی یک IP جعلی یک‌باره نمی‌شود**.
- نصف‌کردن (به‌جای حذف یکی به ازای هر درج) هزینهٔ مرتب‌سازی را روی n/2 درج
  سرشکن می‌کند، نه اینکه روی هر بسته در سقف یک sort اجرا شود.
- تخلیه فقط وقتی صدا زده می‌شود که کلید **جدید** باشد؛ تازه‌سازی یک کلید
  موجود نمی‌تواند نگاشت را رشد دهد.

سه تست جدید: `last_activity_is_bounded_under_spoofed_sources`،
`inbound_ttl_is_bounded_under_spoofed_sources` و
`last_activity_eviction_prefers_the_oldest` — هر سه با
`idle_timeout_secs = 86_400` اجرا می‌شوند تا مطمئن شویم **سقف** کار
می‌کند، نه `flush_idle`.

### ۱۰ 🟠 `autottl.rs::suggest_ttl_scaled` — با مقادیر پیش‌فرض تقریباً همیشه TTL=1

پیش‌فرض‌ها: `a1=0`، `a2=4`، `max=10` (خطوط ۳۱۹–۳۲۰ `config.rs`).

شاخهٔ اول:
```rust
if hops <= a2 {
    hops.saturating_sub(a2.saturating_sub(1)).max(1)
}
```
با `a2=4`: `hops - 3`، سپس `.max(1)`. برای هر `hops ≤ 4` نتیجه **۱** است.
یک بستهٔ TTL=1 حتی از اولین روتر هم رد نمی‌شود، چه رسد به رسیدن به DPI —
یعنی تکنیک decoy کاملاً بی‌اثر می‌شود.

همچنین `a1` با `a1.max(1)` به ۱ کف‌گذاری می‌شود، پس مقدار پیش‌فرض `0`
هیچ‌وقت واقعاً استفاده نمی‌شود — نشانهٔ اینکه پیش‌فرض‌ها با الگوریتم
هماهنگ نیستند.

**این تابع هیچ تستی ندارد.** هر ۴ تست `autottl` روی `suggest_ttl` معمولی‌اند.

**✅ رفع انجام‌شده:** ریشهٔ مشکل این بود که مقیاس **وارونه** بود — مسیرهای
کوتاه کاهش بزرگ (`a2`) و مسیرهای دور کاهش کوچک (`a1`) می‌گرفتند، که هم
برعکس منطق تکنیک است و هم روی پیش‌فرض‌ها به TTL=1 فرو می‌ریخت.

فرمول بازنویسی شد به:
```text
decoy_ttl = clamp(hops - reduction(hops), 1, min(m, MAX_AUTO_TTL))
reduction = a1 + min(hops/m, 1) * (a2 - a1)   // گرد شده، کف ۱
```
یعنی کاهش **با فاصله زیاد می‌شود**: روی مسیر کوتاه محافظه‌کارانه می‌بُرد
(فاصلهٔ کمی بین «به DPI می‌رسد» و «به مقصد می‌رسد» هست) و روی مسیر بلند
حاشیهٔ بزرگ‌تری می‌گیرد. `hops == 0` (همسایهٔ on-link) حالا به همان
پیش‌فرض امن `4` برمی‌گردد که `suggest_ttl` استفاده می‌کند، نه TTL=1.

منحنی جدید با پیش‌فرض‌ها (شبیه‌سازی مستقل):

| observed TTL | hops | decoy TTL (قبل) | decoy TTL (بعد) |
|---|---|---|---|
| ۶۴ | ۰ | ۱ | **۴** |
| ۶۰ | ۴ | ۱ | **۲** |
| ۵۸ | ۶ | ۱ | **۳** |
| ۵۶ | ۸ | ۵ | **۵** |
| ۵۴ | ۱۰ | ۶ | **۶** |
| ۵۰ | ۱۴ | ۱۰ | **۱۰** |

**شش تست جدید** اضافه شد (تابع قبلاً صفر تست داشت):
`scaled_does_not_collapse_to_one_on_short_paths` (رگرسیون اصلی)،
`scaled_is_below_the_hop_count`، `scaled_is_monotonic_in_distance`
(منحنی باید یکنوا باشد — نسخهٔ وارونهٔ قبلی این را رد می‌کرد)،
`scaled_respects_the_m_ceiling_and_hard_cap`،
`scaled_on_link_peer_uses_safe_default`،
`scaled_normalises_degenerate_parameters`.

هر شش تست با شبیه‌سازی مستقل منطق در پایتون اجرا و **سبز** شدند.

### ۱۱ 🟡 `relay.rs` — اسلات flow در مسیر fail-closed آزاد نمی‌شود

در `handle_conn`، `on_flow(flow)` یک ورودی در `relay_flows` ثبت می‌کند.
وقتی fail-closed فعال شود (`require_inject && !ok`)، تابع `drop(server);
drop(client); return Ok(())` می‌کند — بدون هیچ اطلاعی به pipeline.

ورودی تا `flush_idle` (۱۲۰ ثانیه) باقی می‌ماند. تحت شکست پیوستهٔ injection،
جدول ۲۵۶‌تایی پر می‌شود و لاگ «evicted the oldest live flow» ظاهر می‌شود —
که باعث می‌شود اتصالات **سالم** هم قابل تأیید نباشند و آن‌ها هم fail-closed
شوند. یک حلقهٔ تشدیدشونده.

**✅ رفع انجام‌شده:** به‌جای وصلهٔ نقطه‌ای روی شاخهٔ fail-closed، مسئله با
**RAII** حل شد تا هیچ مسیر خروجی (حالا یا در آینده) نتواند از قلم بیفتد:

- کالبک تکی `on_flow` با `FlowHooks { register, unregister }` جایگزین شد.
- ساختار `FlowSlot` که `Drop`ش `unregister` را صدا می‌زند، بلافاصله پس از
  `register` ساخته می‌شود. حالا **هر** بازگشت از `handle_conn` — خطای
  connect، تایم‌اوت connect، drop مربوط به fail-closed، پایان عادی حلقهٔ
  کپی، و حتی یک panic احتمالی — اسلات را آزاد می‌کند.
- `Pipeline::unregister_relay_flow(flow) -> bool` اضافه شد و idempotent
  است، پس یک drop دوتایی نمی‌تواند flow نامرتبطی را که همان ۴-تایی را
  دوباره استفاده کرده حذف کند.
- `main.rs` حالا دو کلون از `Arc<Mutex<Pipeline>>` می‌گیرد (یکی برای هر
  کالبک) و هر دو از `recover_mutex` استفاده می‌کنند.

سه تست جدید: `flow_slot_unregisters_on_drop` (دقیقاً یک بار، و نه پیش از
موعد)، `repeated_fail_closed_connections_do_not_accumulate` (۱۰۰۰ اتصال
fail-closed پشت‌سرهم → مجموعهٔ زندهٔ نهایی باید خالی باشد) و
`fail_closed_churn_never_exhausts_the_relay_table` (۴× ظرفیت جدول →
شمارندهٔ زنده هرگز از ۱ بالاتر نمی‌رود).
