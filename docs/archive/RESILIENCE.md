# RESILIENCE.md — مقاومت در برابر قطعی و اختلال اینترنت

این سند توضیح می‌دهد `dpi_guard` در برابر شرایط واقعی اینترنت ایران
(قطعی مکرر، packet loss بالا، افت سرعت ناگهانی، reset شدن آداپتور شبکه،
خواب/بیدار شدن ماشین) چه رفتاری دارد.

> **صداقت دربارهٔ تست:** در محیطی که این تغییرات نوشته شدند نه Rust
> toolchain نصب بود نه `crates.io` در دسترس. بنابراین `cargo test` اجرا
> **نشده**. آنچه واقعاً اجرا شده: ۲۸۵ بررسی خودکار در `uitest/`
> (`npm test`) که یا کد واقعی را اجرا می‌کنند یا حضور یک مکانیزم را در
> منبع اثبات می‌کنند — و برچسب هر کدام مشخص است. تست‌های Rust جدید در CI
> اجرا می‌شوند.

---

## ۱) Retry با Exponential Backoff

| مسیر | رفتار | سقف |
|---|---|---|
| `engine.rs` — خطای `recv` درایور | backoff نمایی: ۲۰، ۴۰، ۸۰، … میلی‌ثانیه | **۵۰۰ms** |
| `doh.rs` — درخواست DoH | ۳ تلاش با فاصلهٔ ۲۵۰، ۵۰۰ میلی‌ثانیه | **۲s** بین تلاش‌ها |
| رله → کلاینت (v2rayN) | عمداً retry **نمی‌کند**؛ سریع شکست می‌خورد تا کلاینت خودش تلاش مجدد کند | — |
| `main.rs` — رلهٔ بالا-نیامده | هر **۳۰ ثانیه** یک‌بار دوباره start می‌شود | — |

**چرا رله per-connection retry ندارد؟** چون رله یک پاس‌دهندهٔ شفاف است؛
نگه‌داشتن سوکت کلاینت برای تلاش مجدد فقط v2rayN را معطل می‌کند. منطق
تلاش مجدد جای درستش در کلاینت است. کاری که رله می‌کند این است که **سریع
و با دلیل مشخص** شکست بخورد.

**باگی که اینجا رفع شد:** قبلاً مسیر خطای `recv` هیچ backoff نداشت:

```rust
// قبل — حلقهٔ بی‌پایان بدون تأخیر
log::warn!("WinDivert recv error, continuing: {e}");
continue;
```

وقتی آداپتور reset می‌شود یا لینک مدام قطع/وصل می‌شود، `recv` بلافاصله و
پیوسته خطا می‌دهد. نتیجه: **یک هستهٔ CPU روی ۱۰۰٪** و یک خط لاگ در هر
چرخه (که اگر لاگ به فایل برود، بی‌نهایت رشد می‌کند). حالا backoff دارد و
لاگ هم rate-limit شده (خط اول، بعد هر صدمین).

## ۲) Timeout منطقی روی هر انتظار شبکه‌ای

| انتظار | مقدار | منبع |
|---|---|---|
| یک درخواست DoH | **۵ ثانیه** (قبلاً ۱۰) | `doh::DOH_TIMEOUT` |
| بودجهٔ کل DoH (۳ تلاش + backoff) | **≤ ۲۱ ثانیه** | تست `total_retry_budget_is_bounded` |
| connect خروجی رله | **۱۰ ثانیه** | `relay::CONNECT_TIMEOUT` |
| تأیید تزریق SNI جعلی | **۳ ثانیه** | `relay::FAKE_ACK_WAIT` |
| انتظار کلاینت (connect + inject) | **≤ ۱۵ ثانیه** | تست `client_facing_wait_is_bounded` |
| پکت نگه‌داشته‌شده (watchdog) | **۲۰۰ms** | `pipeline::HOLD_TIMEOUT` |
| آماده‌شدن capture هنگام start | **۳ ثانیه** | `engine::wait_until_capture_ready` |

**باگی که اینجا رفع شد:** `socket.connect()` در رله **هیچ timeout نداشت**.
روی لینک قطع‌شده، SYN به مقصد غیرقابل‌دسترس تا timeout خود TCP ویندوز
(چند ده ثانیه) معلق می‌ماند و در تمام آن مدت سوکت پذیرفته‌شدهٔ کلاینت باز
نگه داشته می‌شد — یعنی v2rayN هم همراهش آویزان می‌شد. این دقیقاً همان
حالتی است که کاربر «هنگ کردن برنامه» می‌بیند.

## ۳) مدیریت خطا: کرش نمی‌کند، منتظر اتصال مجدد می‌ماند

- مسیر پکت داخل `catch_unwind` است (`fail_open.rs`): **panic یا Err →
  پکت اصلی بدون تغییر re-inject می‌شود**. یک باگ در جهش SNI هرگز اتصال
  شما را سیاه‌چاله نمی‌کند.
- `overflow-checks = true` و `panic = "unwind"` در `[profile.release]` —
  سرریز عددی به جای UB تبدیل به panic می‌شود و همان fail-open آن را
  می‌گیرد.
- مسموم‌شدن Mutex مسیر پکت را از کار نمی‌اندازد (`recover_mutex`).
- خطای `recv` حلقهٔ capture را متوقف نمی‌کند؛ backoff می‌خورد و ادامه
  می‌دهد.

**باگی که اینجا رفع شد (مهم‌ترین مورد برای اینترنت قطع‌وصل‌شونده):**
اگر هنگام بالا آمدن برنامه اینترنت قطع بود، resolve مقصد شکست می‌خورد و
رله بالا نمی‌آمد. ولی `reconcile` **فقط وقتی صدا زده می‌شد که فایل
کانفیگ تغییر کرده باشد**. یعنی رله تا وقتی که اپراتور دستی
`dpi_guard.toml` را دست نمی‌زد، **هرگز** دوباره تلاش نمی‌کرد — حتی ساعت‌ها
بعد که اینترنت برگشته بود.

حالا هر ۳۰ ثانیه بررسی می‌شود: اگر رله در کانفیگ خواسته شده ولی در حال
اجرا نیست، دوباره start می‌شود (`RelayRuntime::wants_but_not_running`).

> **معاوضهٔ این راه‌حل، صریح:** `reconcile` مقصد را به‌صورت همگام resolve
> می‌کند، پس در لحظهٔ تلاش مجدد این ترد تا ~۱۶ ثانیه بلاک می‌شود و
> flush پکت‌های نگه‌داشته‌شده به همان اندازه عقب می‌افتد. این فقط وقتی
> رخ می‌دهد که رله **خاموش** است، و حداکثر هر ۳۰ ثانیه یک‌بار. راه‌حل
> درست (که در کد هم به آن اشاره شده) این است که resolve روی ترد جدا
> انجام شود و آدرس آماده به `reconcile` داده شود.

## ۴) ذخیرهٔ وضعیت و ادامه از نقطهٔ قطع

ماژول جدید `src/dns_cache.rs`:

- پاسخ‌های موفق DoH در حافظه کش می‌شوند (TTL = ۵ دقیقه).
- کش روی دیسک هم mirror می‌شود: `dpi_guard.dns_cache` **کنار exe** (نه
  cwd — همان استدلال قفل تک‌نمونه و جست‌وجوی درایور).
- نتیجه: اگر برنامه **در زمان قطعی** restart شود، هنوز می‌تواند مقصد
  رله را از کش روی دیسک بخواند و بالا بیاید.
- ورودی‌های قدیمی‌تر از `MAX_STALE` (۶ ساعت) هنگام load دور ریخته
  می‌شوند.
- سقف فایل ۶۴ KiB، سقف حافظه ۲۵۶ ورودی؛ فایل خراب/بزرگ → کش خالی، نه
  خطا.
- **همهٔ آدرس‌های کش‌شده قبل از استفاده دوباره از
  `netguard::validate_relay_ip` رد می‌شوند**، پس یک فایل کش دستکاری‌شده
  نمی‌تواند رله را به مقصد ممنوعه (loopback/metadata) بفرستد.
- این فایل در `.gitignore` است چون می‌تواند IP سرور شما را داشته باشد.

## ۵) حالت آفلاین / کش

وقتی **همهٔ** تلاش‌های DoH شکست بخورند:

1. اگر کش ورودی تازه دارد → همان برگردانده می‌شود (لاگ: `fresh`).
2. اگر ورودی منقضی ولی younger از ۶ ساعت دارد → برگردانده می‌شود با
   لاگ صریح **`STALE`**.
3. در غیر این صورت → خطا.

این برای این پروژه امن است چون نام کش‌شده **مقصد رلهٔ خودِ اپراتور** است،
نه یک lookup دلخواه. «آدرس قدیمی سرور خودت» به «هیچ اتصالی» ارجحیت دارد.

**نکتهٔ مهم:** اگر `relay_connect_host` را **IP literal** بگذارید
(مثلاً `1.1.1.1`)، اصلاً DNS زده نمی‌شود — نه DoH، نه UDP/53. این
**قوی‌ترین** گزینه برای اینترنت بی‌ثبات است و در `START_HERE.md` هم
توصیه شده.

## ۶) تنظیمات توصیه‌شده برای اینترنت بی‌ثبات

```toml
# مقصد را IP literal بگذارید تا کل مسیر DNS حذف شود
relay_connect_host = "1.1.1.1"

# fail-closed را روشن نگه دارید؛ خاموش‌کردنش محافظت را از بین می‌برد
relay_require_inject = true

# TTL پکت جعلی را با tracert اندازه بگیرید، نه حدسی
decoy_ttl = 8

# اگر connection drop زیاد می‌بینید، AutoTTL را روشن کنید تا TTL از
# hop count ورودی یاد گرفته شود
enable_autottl = false
autottl_delta = 0

# QUIC bypass فقط وقتی لازم است؛ روی لینک بی‌ثبات یک متغیر اضافه است
enable_quic_port_bypass = false
```

## ۷) تشخیص مشکل

| علامت در لاگ | معنی | اقدام |
|---|---|---|
| `WinDivert recv error (N in a row), backing off` | آداپتور reset شده یا درایور مشکل دارد | اگر N بزرگ شد، درایور/آداپتور را بررسی کنید |
| `DoH attempt 2/3 ... failed` | packet loss روی مسیر DoH | طبیعی است؛ retry ادامه می‌دهد |
| `falling back to a STALE cached answer` | DoH کامل شکست خورده، از کش استفاده شد | `relay_connect_host` را IP literal کنید |
| `relay: connect timed out after 10s` | مقصد غیرقابل‌دسترس یا لینک قطع | منتظر بمانید؛ هر ۳۰ ثانیه دوباره تلاش می‌شود |
| `relay is configured but not running — retrying start` | رله قبلاً بالا نیامده، در حال تلاش مجدد | طبیعی است |
| `fake injection not confirmed ... dropping connection` | fail-closed درست کار کرده؛ pipeline هندشیک را ندیده | فیلتر WinDivert و پورت مقصد را بررسی کنید |
